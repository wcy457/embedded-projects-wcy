## 0. 一分钟电梯陈述(背下来)

> 这个项目是一个双工程结构的嵌入式系统:一个 16KB 的自研串口 IAP Bootloader 加一个 FreeRTOS 业务固件。Bootloader 自定义升级帧协议,通过 USART1 + DMA 分块接收固件,CRC32 整包校验后安全跳转到 APP;跳转前做了完整的现场清理——停 SysTick、清 NVIC、反初始化外设、重设 MSP 和 VTOR,并对 APP 镜像做合法性校验。业务固件跑 FreeRTOS,划分了 7 个固定周期任务,实现编码器测速 + 位置式 PID 风速闭环、温湿度/烟气多传感器加权融合、自动模式三态状态机和带迟滞去抖的防倒灌检测。串口升级通道的上位机协议做了传输层解耦,PC 模拟的是产线烧录器或 WiFi OTA 模组的角色。

## 1. Bootloader 深度讲解

源文件:`bootloader YJ/BSP_BOOT/bootloader.c`、`bootloader.h`、`crc32.c`

### 1.1 上电启动流程

```c
int main(void)
{
    HAL_Init();                     /* SysTick 初始化(1ms tick) */
    SystemClock_Config();           /* 72MHz */
    MX_GPIO_Init();                 /* PB0 升级按键 */
    MX_DMA_Init();
    MX_USART1_UART_Init();          /* 115200, RX 走 DMA Normal */

    if(!boot_is_key_pressed())      /* 没按 PB0:尝试跳 APP */
    {
        (void)boot_jump_to_app();   /* 返回 0 = APP 无效,顺延进升级模式 */
    }
    boot_run_update();              /* 升级主循环,永不返回 */
}
```

面试要点:**没有按键也不代表直接进升级**——先尝试跳 APP,APP 无效(返回 0)才留在升级模式。所以空芯片/升级失败芯片上电后自动处于"待接收固件"状态,这是"不变砖"体验的关键。

### 1.2 DMA 分块接收(带超时 + 错误检测)

```c
static uint8_t uart_dma_block_recv(uint8_t *dst, uint16_t n, uint32_t timeout_ms)
{
    uint32_t tickstart;

    if(HAL_UART_Receive_DMA(&huart1, dst, n) != HAL_OK)
        return 0U;                          /* DMA 启动失败 */

    tickstart = HAL_GetTick();
    while(huart1.RxState != HAL_UART_STATE_READY)
    {
        if((HAL_GetTick() - tickstart) > timeout_ms)
        {
            (void)HAL_UART_AbortReceive(&huart1);
            return 0U;                      /* 超时,放弃本次接收 */
        }
    }

    /* ORE/FE 等错误会让 HAL 提前回到 READY,但字节没收够 */
    if((huart1.hdmarx != NULL) && (__HAL_DMA_GET_COUNTER(huart1.hdmarx) != 0U))
        return 0U;
    return 1U;
}
```

**四个必讲细节:**

1. **为什么轮询 `RxState` 而不用信号量?** Bootloader 是裸机(没有 RTOS),DMA 传输完成中断会把 `RxState` 置回 `READY`,轮询是最简单可靠的同步方式。
2. **超时判断写法 `(HAL_GetTick() - tickstart) > timeout_ms`:** `HAL_GetTick()` 是 32 位无符号数,约 49.7 天回绕。无符号减法天然处理回绕(数学上 `a-b mod 2^32` 恒正确),这是面试高频题,标准答案就是"无符号整数减法的模运算特性"。
3. **`__HAL_DMA_GET_COUNTER` 的妙用:** 串口线路错误(ORE 溢出/FE 帧错误)会让 HAL 内部提前终止接收、`RxState` 变 READY,但 DMA 计数器(NDTR)还没减到 0——即字节没收够。用"READY 但 NDTR≠0"判定异常,比单纯等 READY 更健壮。
4. **超时后必须 `AbortReceive`:** 释放 UART/DMA 句柄状态,否则下一次 `HAL_UART_Receive_DMA` 返回 BUSY。

**三级超时:** 帧头 2000ms(等用户操作,可以长)、数据块 1000ms(128B @115200 只要 11ms,1s 很宽裕)、CRC 尾 1000ms。

### 1.3 Flash 编程细节(F1 的物理约束)

```c
static void flash_write_byte(uint8_t b)
{
    s_word_buf |= ((uint32_t)b) << (s_byte_cnt * 8U);  /* 小端序攒字节 */
    s_byte_cnt++;

    if(s_byte_cnt == 4U)
    {
        if(HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, s_flash_write_addr, s_word_buf) != HAL_OK)
        {
            Error_Handler();          /* 编程失败必须处理,不能静默 */
        }
        s_flash_write_addr += 4U;
        s_word_buf = 0U;
    }
}
```

- **F1 只支持按字(32bit)编程**,串口来的是字节流 → 用 `s_word_buf` 攒 4 字节再编程,攒够 4 字节才写一次。
- **擦除后 Flash 全为 0xFF,编程只能把 1 改成 0。** 固件长度不是 4 的整数倍时,`flash_write_flush()` 用 0xFF 填满最后一个字再编程——填 0xFF 等于"没改",不会破坏数据。
- **擦除是按页的**(F103 中容量 2KB/页),全片擦除循环 248 页,失败返回 0、上层 Lock 后重试:

```c
while(cur_addr < (APP_BASE_ADDR + APP_MAX_SIZE))
{
    erase_cfg.TypeErase    = FLASH_TYPEERASE_PAGES;
    erase_cfg.PageAddress  = cur_addr;
    erase_cfg.NbPages      = 1U;
    if(HAL_FLASHEx_Erase(&erase_cfg, &page_error) != HAL_OK)
        return 0U;
    cur_addr += F1_FLASH_PAGE_SIZE;
}
```

### 1.4 CRC32(与上位机交叉验证)

```c
/* 反射式 CRC32(多项式 0xEDB88320),初值/结果均异或 0xFFFFFFFF */
crc = (crc >> 1) ^ (0xEDB88320u & (uint32_t)(0u - (crc & 1u)));
```

- `0xEDB88320` 是标准 CRC-32 多项式 `0x04C11DB7` 的**位反转形式**(反射算法从低位算)。
- **特意实现成与 Python `zlib.crc32` 结果一致**——上位机 `zlib.crc32(data)` 直接算,bootloader 流式算,两边结果可互相验证,这是我上位机能用标准库的原因(见 `tools/ota_host.py`)。
- 流式接口:`crc32_update` 逐块更新,`crc32_finalize` 末尾异或,适合"边收边算"。

### 1.5 跳转 APP 的五个步骤(每步都要能讲为什么)

```c
uint8_t boot_jump_to_app(void)
{
    /* 0. 取 APP 向量表前两字:初始 MSP + 复位向量 */
    app_msp_stack    = *(volatile uint32_t *)APP_BASE_ADDR;
    app_reset_entry  = *(volatile uint32_t *)(APP_BASE_ADDR + 4U);

    if(boot_is_app_valid(app_msp_stack, app_reset_entry) == 0U)
        return 0U;                          /* APP 无效,留在升级模式 */

    /* 1. 停掉 bootloader 的 SysTick */
    SysTick->CTRL = 0U;  SysTick->LOAD = 0U;  SysTick->VAL = 0U;

    /* 2. 关闭并清除全部 NVIC 中断使能与挂起 */
    for(idx = 0U; idx < 8U; idx++)
    {
        NVIC->ICER[idx] = 0xFFFFFFFFU;      /* 8 个 ICER 覆盖 240 个外设中断 */
        NVIC->ICPR[idx] = 0xFFFFFFFFU;
    }

    /* 3. 反初始化 bootloader 用过的外设 */
    HAL_UART_DeInit(&huart1);
    HAL_DMA_DeInit(&hdma_usart1_rx);
    HAL_DMA_DeInit(&hdma_usart1_tx);

    /* 4. 向量表重定位 */
    SCB->VTOR = APP_BASE_ADDR;

    /* 5. 关中断 → 切主栈指针 → 跳复位向量 */
    __disable_irq();
    __set_MSP(app_msp_stack);
    ((void (*)(void))app_reset_entry)();
}
```

**为什么每一步(面试最高频):**

| 步骤 | 不做会怎样 |
|---|---|
| 停 SysTick | 已挂起的 SysTick 异常在跳转后触发,打到 APP 刚配置一半的向量表 → 跑飞 |
| 清 ICER/ICPR | Boot 使能的 USART/DMA 中断,APP 里若没写对应 handler,C 启动文件的弱符号 `Default_Handler` 死循环;挂起标志不清会"补触发" |
| DeInit 外设 | UART/DMA 停在中间状态(如半块 DMA 未完成),APP 的 `MX_*_Init` 假设寄存器是复位态,可能配置失败或行为异常 |
| 设 VTOR | 不设的话中断仍取 bootloader 区向量(旧函数地址 + 新 MSP = 灾难)。APP 的 SystemInit 里 `VECT_TAB_OFFSET 0x4000` 会再设一次,双保险 |
| `__disable_irq()` 后再 MSP | `__set_MSP` 改栈指针的瞬间若来了中断,压栈会写坏栈;关中断窗口极短,APP 启动后自己会开 |
| 从向量表[0] 取 MSP | APP 的栈位置只有 APP 自己知道,硬编码非法;向量表第 0 字就是链接器安排的栈顶 |
| 入口 bit0=1 | Cortex-M 的 Thumb 状态要求函数地址 bit0=1,直接赋 PC 时是硬件行为要求 |

**镜像合法性校验(防跳空片/坏镜像):**

```c
static uint8_t boot_is_app_valid(uint32_t msp, uint32_t entry)
{
    if((msp < RAM_BASE_ADDR) || (msp >= RAM_END_ADDR))        return 0U;  /* 0x20000000~0x20010000 */
    if((entry < APP_BASE_ADDR) || (entry >= APP_FLASH_END_ADDR)) return 0U;
    if((entry & 1U) == 0U)                                     return 0U;  /* Thumb 位 */
    return 1U;
}
```

实测数据:APP hex 向量 `MSP=0x20004E30`(在 SRAM 内)、`entry=0x08004279`(bit0=1)→ 校验通过。

### 1.6 升级协议与握手时序

帧结构:`[4B 小端 payload 长度][payload 固件][4B 小端 CRC32]`,接收顺序 = 状态机顺序。

```
 上位机(PC/未来WiFi模组)                Bootloader
        │  [4B 长度]                        │ 收长度→合法性检查→Unlock→全片擦除(约5s)
        │◄────────────────'R'(擦除完成)─────│ ← 关键握手!擦除期间发数据必丢
        │  [固件, 128B/块, 块间10ms]         │ 每块: DMA收满→按字写Flash→更新CRC
        │  [4B CRC32]  (发前延时20ms)        │ flush 最后一字→Lock→比对CRC
        │◄──────────────'K' 或 'N'──────────│ 'K'=通过→跳转; 'N'=失败→等整帧重发
```

**协议设计答辩口径:**

- 为什么不用 XMODEM:XMODEM 逐块 ACK 是停等协议,496KB 会慢十几秒;它没有总长度字段,靠 EOT+填充判断镜像边界。我的场景是"一次性整包传输 + 先擦后写",长度前缀直接决定擦写范围,整包 CRC32 一次验收,状态机百行内。
- 为什么加 ACK:原方案盲发,丢字节只能靠 CRC "验尸"。加 1 字节 ACK/NAK 后有了自动重传,只花约 350B 代码。
- 上位机时序配合(都是上机会踩的坑):① 全片擦除约 5s,必须等 'R';② bootloader 写最后一块+flush 的几毫秒空窗里 CRC 尾会丢,发 CRC 前延时 20ms;③ 块间隔 10ms 要覆盖"写 32 字 + 重启 DMA"的空窗(约 5ms),否则下一块前几字节丢。

### 1.7 已知局限与演进方向(主动讲,加分)

1. 无**双区备份(A/B)**:升级中掉电 → APP 区被擦 → 只能重传。工业方案:双区 + 状态标志 + 回滚。
2. 无**固件签名/加密**:任何人可刷任意固件;演进:eMMC/Flash 里存公钥,验签后再写入。
3. 无**版本防回滚**、无逐包断点续传。
4. 串口无流控依赖延时规避 → 协议层解耦后可整体换成 CAN/UDS 或模组 OTA,主控侧协议不变。

### 1.8 从上电到 main() 的完整链路(面试常从这问起)

**BOOT 引脚配置(必背):** 本项目 `BOOT0=0`(从主 Flash 启动),芯片把 `0x08000000` 映射到取指地址 `0x00000000`。上电后 CPU 自动做两件事:**从地址 0 取 MSP 初值、从地址 4 取复位向量**——这就是为什么任何固件的前 8 字节必须是 `[栈顶][Reset_Handler]`,也是 `boot_is_app_valid()` 校验这两个字的原因。

```
上电 → CPU 硬件取 MSP/Reset向量(不需要任何软件)
     → startup_stm32f103xe.s:Reset_Handler
         ① 把 .data 段从 Flash(Load 区)拷到 RAM(Exec 区)
         ② .bss 段清零
         ③ 调 SystemInit()(时钟初始化、设 VTOR)
         ④ 跳 __main(ARM C 库:堆栈/库初始化)→ 进入用户 main()
```

**Map 文件四个数(必会解读):** `Code`(代码)/`RO-data`(常量,如字符串表)/`RW-data`(已初始化变量,Flash 里有初值 + RAM 里要运行)/**ZI-data**(零初始化,只占 RAM)。本项目 APP:`Code=22060 RO=460 RW=180 ZI=19836`——RAM 里 ZI 主要是 FreeRTOS 堆,这直接回答"你的 20KB RAM 都花哪了"。

**hex 与 bin 的区别(和升级直接相关):**
- hex 是 Intel HEX 文本格式,自带地址信息:`:02000004 0800` 是扩展线性地址(高 16 位),`:10 4000 00 304E0020...` 数据记录中 `4000` 是低 16 位偏移,两者相加才是真实地址 `0x08004000`——**只看 ELA 记录就喊"基址错了"是常见误判**
- bin 是纯二进制,不带地址,上位机发固件用 bin(本项目的 `test_fw.bin` / `fromelf --bin` 产物),基址由协议+分区约定

### 1.9 故障现象排查速查表(上机调试经历的真实弹药)

| 现象 | 最可能原因 | 定位手段 |
|---|---|---|
| 跳转后 APP 跑飞/HardFault | NVIC 未清、VTOR 未设、MSP 错、入口 Thumb 位丢 | 逐项对照 1.5 五步;Keil 调试看 MSP/PC 落点 |
| CRC 永远校验失败 | 块间隔不够丢字节;擦除期间发了数据;ORE 错误 | 串口抓包比对;增大 inter-delay/确认等 'R' |

| 编译过但 APP 覆盖了 bootloader | Keil Target 里 IROM 起始还是 0x08000000(改了向量表没改链接地址) | 看 map 文件 LR_IROM1 基址 |

### 1.10 Bootloader 追问链(15 题,由浅入深,面试官就是按这个顺序挖)

以下按面试官追问顺序,答案为口头回答口径。

**Q1:Bootloader 自己用什么栈?**

复位之后 MSP 直接取自 bootloader 自己向量表的第 0 项,也就是说 bootloader 全程用的是它向量表里指定的那块栈。等到要跳 APP 时,我在跳转前用 `__set_MSP` 把主栈指针切到 APP 向量表的第 0 项。所以**两个阶段各用各的栈**,bootloader 的栈和 APP 的栈互不干扰。

**Q2:Bootloader 里用中断吗?**

用的,而且离不开。DMA 收满一块会产生传输完成中断,由它把 `RxState` 置回 READY,我的轮询循环才知道"这块收完了"。正因为如此,`stm32f1xx_it.c` 里的 USART1、DMA1_Ch4、DMA1_Ch5 这几个中断服务函数必须保留——这也是我在源码头注释里专门写 NOTE 提醒的原因。

**Q3:收 4 字节和收 128 字节区别?**

本质上是同一个函数 `uart_dma_block_recv`,只是传入的长度 n 不同,DMA NDTR 的装载值不同而已。收帧头就传 4,收数据块就传 128,接收逻辑和超时处理完全复用,基本是零成本的复用。

**Q4:对长度字段做什么检查?**

两条:`len == 0` 直接弃帧,`len > APP_MAX_SIZE - 4` 也直接弃帧。这两条挡住的是零长度帧和超出 APP 区的固件,不给后面的擦除、写入任何**越界擦写**的机会。

**Q5:CRC 为什么整包而不是每块?**

这是我主动做的权衡。整包校验的好处是重传逻辑最简单:校验不过就回 'N',上位机整帧重发。如果每块都带 CRC 加块号,那就是 XMODEM 的思路,代价是逐块停等确认——496KB 固件在串口上停等开销太大。所以我选了"**整包验收 + NAK 整帧重传**"这个方案。

**Q6:发 'K' 后立刻跳转,上位机来得及收吗?**

来得及。`HAL_UART_Transmit` 是**阻塞发送**,返回时最后一个字节已经完全移出发送移位寄存器,所以 'K' 一定是完整发出去的,不会被跳转动作截断。

**Q7:`__disable_irq()` 后,APP 里谁负责开中断?**

`__disable_irq` 置的只是 PRIMASK 这个掩码位,APP 的启动代码和 CubeMX 初始化流程会把它恢复。这里要分清两层:关中断(PRIMASK)和清 ICER 是**两个独立机制**,跳转前两层都要处理——只关 PRIMASK 不够,还得把 NVIC 里 bootloader 开过的中断全部清掉。

**Q8:为什么不失败就回滚旧固件?**

因为单区方案里根本没有"旧固件"可回滚——我是先全片擦除再写入,擦完那一刻旧固件就不存在了。想支持回滚必须上**双区 A/B 加状态标志**,这是我很明确的演进方向,不是没考虑到。

**Q9:Bootloader 怎么压到 8.4KB?**

两个手段。一是 HAL 只编入真正用到的模块——GPIO、DMA、UART、FLASH、FLASHEx,不引入 printf 和动态内存这类会把整个库拉进来的依赖;二是 bootloader 工程里完全不含 APP 侧的 FreeRTOS,两边物理隔离,体积自然可控。

**Q10:上位机发 500KB 固件怎么办?**

在长度检查那一关就被直接拒帧——500KB 超过 APP 区上限,连擦除都不会开始,更不可能越界擦写。这就是帧头带长度前缀的价值:**边界检查发生在碰 Flash 之前**。

**Q11:VTOR 每次中断都重新读吗?**

不用,设置一次即可,硬件在每次异常取址时会自动引用 VTOR。另外 APP 的 SystemInit 还会再设一次,跟 bootloader 里设的值等价,等于双保险。

**Q12:bootloader 需要喂狗吗?**

本项目没启用 IWDG,所以不存在这个问题。但我知道这个坑在哪:如果启用了看门狗,全片擦除那几秒和整个升级循环里都必须插喂狗,否则升级到一半会被狗咬复位,升级直接失败。

**Q13:写 Flash 时丢了几个字节怎么办?**

有两道网兜着。接收端这边,NDTR≠0 能检出 DMA 提前终止这类异常;就算漏过去,丢了字节的整包 CRC 必然对不上。两条路最终都回 'N',上位机整帧重传,重传时重新擦除从头写。安全性由"**先擦后写 + 整包校验**"这个组合兜底,不依赖单一环节。

**Q14:量产时怎么烧 bootloader?**

SWD 或治具只在产线上烧一次 bootloader,之后产品的整个生命周期固件升级全走串口 IAP,不用再拆机。这就是 IAP 方案的商业价值:一次治具成本,换来终身可升级。

**Q15:上位机协议跟 WiFi 模组怎么衔接?**

传输层是**解耦**的。模组从云端拉到固件后,按同一套帧格式把字节流透传进来就行,bootloader 完全不感知对端是 PC 还是模组——协议跟介质无关,这是当初把协议设计成裸字节流的回报。

### 1.11 升级时间与带宽预算(会算时间 = 懂系统)

面试官问"升级一次要多久/慢不慢",能现场用波特率算出来,立刻和背书的人拉开差距。

**基础参数:** 115200 8N1 → 每字节 10 bit(1 起始 + 8 数据 + 1 停止)→ **波特率 ÷ 10 = 字节率**。

```
字节率     = 115200 / 10           = 11520 B/s ≈ 11.25 KB/s
每字节耗时 = 1 / 11520             ≈ 86.8 µs
128B 数据块传输 = 128 × 86.8 µs   ≈ 11.1 ms
```

**全片擦除:** APP 区 496KB ÷ 2KB/页 = 248 页,F1 页擦除典型 ~20ms → 约 5s(与实测一致,这就是必须等 'R' 握手的原因)。

**端到端估算(以 100KB 固件为例):**

| 阶段 | 计算 | 耗时 |
|---|---|---|
| 全片擦除 | 248 页 × 20ms | ≈ 5 s |
| 数据传输 | 102400 B ÷ 11520 B/s | ≈ 8.9 s |
| 块间隔(含写 Flash 空窗) | 800 块 × 10ms(其中约 5ms 是"写 32 字 + 重启 DMA",其余是裕量) | ≈ 8 s |
| 握手/重传余量 | — | ≈ 1 s |
| **合计** | | **≈ 23 s** |

**结论口径:** "瓶颈不在波特率,在'收一块写一块'的块间隔和全片擦除。要提速:① 波特率提到 460800;② 块加大到 512B + STM32 侧双缓冲;③ 改成'先收完整包到 SRAM 再统一擦写'(SRAM 不够时收一页写一页)。但串口 IAP 的定位是产线/维保通道,23s 完全可接受。"

### 1.12 与通用升级方案对比(被问"为什么不用 XX"时的弹药)

| 方案 | 块/校验 | 停等? | 依赖 | 典型场景 | 我为什么没选 |
|---|---|---|---|---|---|
| XMODEM | 128B / CRC16 | 是(逐块 ACK) | 无 | 超级终端手工传 | 496KB 停等太慢;无长度字段,镜像边界靠 EOT+填充猜 |

### 1.13 Bootloader 追问链·第二批(进阶 10 题:16~25)

以下按面试官追问顺序,答案为口头回答口径。

**Q16:长度字段为什么放帧头不放帧尾?**

核心原因是状态机必须**先知道"收多少"才有下一步动作**:拿到长度才能做合法性检查(拒 0、拒超界)、才能确定擦写范围、才能定 DMA 每一块的装载量。放在帧尾就成了"收完才知道收了多少",既没法提前拒帧,也没法提前规划擦写,整个流程就倒过来了。

**Q17:CRC 为什么放尾部、整包一次?**

整包 CRC 本来就只能等数据全部到齐才能算出来。而我在 bootloader 里用 `crc32_update` 做流式计算,**边收块边算**,等 4 字节 CRC 尾到达时只差最后一步 finalize,不需要任何额外缓存——所以放尾部是自然的选择。

**Q18:bootloader 的 RAM 占用多少?**

业务侧占用很小:一个 128 字节的接收缓冲,加上状态机的几个变量。关键是固件**不来整包缓存**——来一块写一块,这是与"先收后写"方案在 RAM 上的本质区别,后者要多花一块跟固件等大的 SRAM。另外 HAL 的 UART/DMA 句柄是库的固定开销,算在库里。

**Q19:两个 Keil 工程怎么保证不互相污染?**

靠工程文件物理隔离。bootloader 工程只编 BSP_BOOT 相关文件,不含 APP 的 FreeRTOS,也不含 Core/main.c;APP 那边 IROM 从 0x08004000 起编。最后还有**双重确认**:看产出的 hex 首地址,再看 map 文件里的 LR_IROM1 基址,两边对得上才算数。

**Q20:APP 运行中想回头升级怎么办?**

思路是让 APP 置一个"升级请求"标志——放 RTC 备份寄存器或 Flash 标志位都行——然后触发软件复位;bootloader 上电先查这个标志,查到就**等效于按了按键**。当前版本用的是 PB0 物理按键,这个标志位方案是我明确的演进点。

**Q21:升级中途拔掉串口线会怎样?**

这个问题要分两个阶段看。第一阶段,擦除期间拔线:全片擦除以 2KB 页为单位,已擦的页就是干净的 0xFF,不会出现"擦了一半的页";第二阶段,收数据时拔线:当前 DMA 块收不满,三级超时兜底(帧头 2s / 数据块 1s / CRC 尾 1s)在任意阶段等不到数据,就调用 `HAL_UART_AbortReceive` 释放 UART/DMA 句柄,状态机直接退回"等帧头"的空闲状态,程序不会死等。

数据完整性有双重保障:**一,帧没收完整,就永远走不到 CRC 比对那一步**,校验不过绝不会跳转;二,APP 区即使被写了一半,下次重发时 `boot_run_update` 会重新 Unlock 并全片擦除,从干净状态重来。而整个升级流程中,bootloader 自己的前 16KB 是任何代码路径都碰不到的。所以无论怎么拔线,最坏结果只是 APP 区脏了,重新插线、按住 PB0 复位、再发一次帧就恢复——**永远不变砖**。

**Q22:固件长度不是 4 的倍数怎么办?**

F1 的 Flash 只支持按字(4 字节)编程,所以我在 `flash_write_flush()` 里用 0xFF 把最后一个字补满再写。补进去的是全 1,而擦除后的 Flash 本来就是全 1,写 0xFF 等于"没写",**数据无损**。

**Q23:怎么证明你的 bootloader 稳定?**

我做了一组**注入测试**,五条路径每条都有明确预期:错 CRC 触发 NAK 整帧重传;中途断流触发超时恢复;连续 10 次整包升级验证可重复性;非法长度帧(0 和超界)验证拒收;非法向量镜像验证镜像校验拒绝。异常路径都有确定行为,而不是"碰巧没出事"。

**Q24:换一颗芯片(如 F407)要改哪里?**

驱动层要动:页大小从 2KB 变成扇区(16KB 起)、页数不同、编程位宽不同(F4 支持字节/半字/字/双字)、时钟树也要重配。但**协议层、CRC、跳转五步全部复用**——这就是分层架构的回报,换芯片只换"腿",不换"脑子"。

**Q25:bootloader 里能用 printf 吗?**

技术上能,但不该。printf 一进来就拉起库依赖,体积多好几 KB。我的 bootloader 只用 `HAL_UART_Transmit` 发单字节握手('R'/'K'/'N'),整个固件 8.4KB——关键路径上,**确定性优先于便利性**。

## 2. FreeRTOS 深度讲解

源文件:`RTOS YJ/APP/tasks.c`、`app_config.h`、`system_state.c`

### 2.1 七个任务总表(必背)

| 代号 | 中文任务名 | 函数 | 周期 | 优先级 | 栈(word) | 职责 |
|---|---|---|---|---|---|---|
| key | 按键任务 | vKeyTask | 10ms | **6** | 128 | 扫描 4 按键,切模式/档位/电源 |
| speed | 测速任务 | vSpeedTask | 50ms | **5** | 256 | 编码器测速 + PID 闭环(手动模式) |
| motor | 电机任务 | vMotorTask | 50ms | **5** | 128 | 读全局占空比 → 写 TIM1 PWM |
| fusion | 融合任务 | vFusionTask | 100ms | **4** | 256 | 融合算 PWM + 自动模式状态机 |
| backflow | 防倒灌任务 | vBackflowTask | 100ms | **4** | 128 | 防倒灌迟滞检测 + 倒灌模式控制 |
| sensor | 传感任务 | vSensorTask | 500ms | **2** | 256 | MQ135 烟气 + DHT11 温湿度采样 |
| ui | 显示任务 | vUiTask | 200ms | **1** | 256 | OLED 分页显示(仿真模式走串口打印) |

**优先级设计逻辑(面试这么讲):**

> 按"响应速度要求 + 控制回路重要性"排:按键是人机交互,要求最快响应(10ms 扫描、最高优先级,但每次工作量极小);速度环和电机输出是 50ms 实时控制闭环,次之;融合/防倒灌是 100ms 级的慢速决策;传感器物理量变化慢(烟气/DHT11 本身刷新率低),500ms 采样足够;UI 最不重要,空闲时间刷新即可。

**栈大小怎么定(必问):**

栈消耗来自三个地方:① 每层函数调用压返回地址和被破坏的寄存器(Cortex-M 一层约 8~16 字节);② 该任务一路调用链上**所有函数局部变量之和**(尤其 float、数组、结构体);③ 库函数内部开销——`snprintf`/`printf` 这类是"吃栈大户",一次调用就可能吃掉上百字节。

按这个口径逐任务看:

| 任务 | 栈(word) | 为什么是这个值 |
|---|---|---|
| key | 128 | 4 次 GPIO 读 + 整数状态机,调用链就 2 层,不碰库函数 → 512B 富余 |
| motor | 128 | 只读全局占空比写 TIM1 CCR,纯寄存器操作,工作量极小 → 512B |
| backflow | 128 | 迟滞检测纯整数逻辑,无库函数,调用链浅 → 512B |
| speed | 256 | PID 三个浮点量(误差/积分/前馈)同时存在,加可能调 printf 调试 → 1KB |
| fusion | 256 | 自动模式状态机 + float 融合运算 + 调 `snprintf` 给 UI 格式化字符串 → 1KB |
| sensor | 256 | DHT11 单总线时序靠 DWT 计数,中间状态变量多 + MQ135 ADC 转 float → 1KB |
| ui | 256 | OLED 分页 + 大量 `snprintf` 格式化 + 局部字符串缓冲区 → 1KB |

**128 和 256 的分界线一句话**:会不会调 `snprintf` 这类吃栈库函数、有没有多个 float 局部变量——沾一样就给 256,都不沾就 128。

**实测兜底**:初值按上表估完后跑全流程,再用 `uxTaskGetStackHighWaterMark()` 看历史最小剩余,FreeRTOS 推荐留 15~20% 余量。同时配 `configCHECK_FOR_STACK_OVERFLOW = 2`,真溢出会触发 hook 进安全态,运行期也兜得住——估算 + 实测 + hook 三层保险。

### 2.2 固定周期调度:`vTaskDelayUntil` 而不是 `vTaskDelay`

```c
static void vKeyTask(void *arg)
{
    TickType_t last = xTaskGetTickCount();
    (void)arg;
    for(;;)
    {
        handle_keys();
        vTaskDelayUntil(&last, pdMS_TO_TICKS(PERIOD_KEY_MS));  /* 绝对时间对齐 */
    }
}
```

- `vTaskDelay(n)` 是"从**现在**起再等 n":执行耗时会被累加进周期,实际周期 = 工作耗时 + n,有抖动。
- `vTaskDelayUntil(&last, n)` 是"从**上次起点**算起对齐 n":保证严格周期(只要工作耗时 < n)。控制回路(speed/motor)对采样周期一致性敏感,必须用它。

### 2.3 共享状态保护:互斥锁 + 临界区的取舍

全局状态结构 `g_state`(模式、目标/实际转速、PWM、温湿度、烟气、事件标志)被 7 个任务读写,用 `state_lock()/state_unlock()`(互斥锁)保护:

```c
/* 典型用法:读-算-写最小化持锁 */
state_lock();
g_state.actual_rpm = rpm;
if(g_state.mode == MODE_MANUAL)
{
    target = (g_state.gear == GEAR_LOW) ? LOW_RPM : HIGH_RPM;
    pwm = manual_pid_step(target, rpm);
    g_state.pwm_duty = pwm;
}
state_unlock();
```

**面试关键对比:为什么 DHT11 用临界区,普通状态用互斥锁?**

```c
taskENTER_CRITICAL();      /* 关中断 */
ok = dht11_read(&t, &h);   /* µs 级位时序采样 */
taskEXIT_CRITICAL();
```

- DHT11 是单总线 µs 级位时序(高电平 26~28µs=0,70µs=1),**RTOS tick 中断(1ms)打进时序中间就丢数据**,必须整段关中断。持锁时间要极短(整个读取 <25ms)。
- 普通 `g_state` 读写只是几条赋值,用互斥锁即可:锁粒度细、不拖累中断延迟。**能在任务级用锁解决的,就不要关中断。**
- 进阶一句:互斥锁 vs 二值信号量的区别是互斥锁有**优先级继承**,可缓解优先级反转——本项目 low(UI)持锁时 high(key)等待,优先级继承防止 middle 任务抢占导致反转。

### 2.4 任务间通信选型:全局状态 + 锁,为什么不用队列?

> 状态语义是"**最新值**"(当前转速、当前占空比),不是"事件流"。队列适合生产者-消费者的消息传递(每条都要消费);最新值语义用"共享结构 + 互斥锁"最直接,任何任务随时读到当前快照。如果演进到事件通知(如按键长按、报警),再加事件队列/任务通知(Task Notification,轻量且更快)。

### 2.6 FreeRTOS 高频追问(基础 6 题)

**Q1:调度方式?**

FreeRTOS 默认是**抢占式 + 同优先级时间片轮转**。抢占指高优先级任务一旦就绪立刻打断低优先级;时间片指同优先级任务每个 tick 轮换一次。本项目 SysTick 配 1ms,speed 和 motor 同为优先级 5,理论上每 tick 互相切一次——但实际两任务周期都是 50ms,绝大多数时间一方在 `vTaskDelayUntil` 阻塞,"轮转"几乎看不到。真正起作用的是**抢占**:按键任务优先级 6 一就绪,立刻打断 5 级的 speed/motor。

**Q2:tick 是多少?**

1ms,由 `configTICK_RATE_HZ = 1000` 决定。这里有个**关键设计**:HAL 时基(`HAL_GetTick`)原本默认走 SysTick,但 SysTick 一旦给了 RTOS 做 1ms 调度心跳,HAL 就不能再用它——否则 `HAL_Delay` 和 RTOS tick 会冲突。所以我在 CubeMX 里把 HAL timebase 切到 TIM4,SysTick 专职 RTOS,HAL 自己用 TIM4 的 1ms 中断喂 `HAL_IncTick`。**两套时基物理隔离,互不干扰**。

**Q3:优先级反转是什么?本项目怎么防?**

经典问题:**低优先级任务持锁,把高优先级任务堵死**。场景是高优等锁 → 锁被中优任务抢走 CPU 持有 → 高优反被中优拖累。FreeRTOS 的互斥锁内置**优先级继承**:低优任务持锁期间被临时抬到等锁任务的优先级,让中优抢不动它,加速释放锁。本项目里 `g_state` 是多任务共享全局状态,所有读写都经 `xSemaphoreTake`(Mutex) 保护——所以即便 speed 和 fusion 都想改 `pwm_duty`,互斥锁 + 优先级继承保证不会出现反转死锁。

**Q4:堆怎么配?**

heap_4 方案,本项目在 .bss/ZI 段里静态分配 `ucHeap[]` 约 20KB。选 heap_4 而不是 heap_1/2/3 的原因是它支持**合并相邻空闲块**(coalesce)+ Free,能应付任务动态创建/删除产生的碎片;而 heap_1 不支持 Free、heap_2 不合并、heap_3 直接套 C 库 malloc 不可控。所有任务的 TCB + 栈 + 队列 + 信号量都从这 20KB 分配,**启动时一次性创建 7 个任务,运行期不再动态申请**——确定性优先。

**Q5:怎么定位栈溢出?**

两步:① 编译期开 `configCHECK_FOR_STACK_OVERFLOW = 2`,任务切换时检查栈底 magic 字(0xA5A5A5A5),越界立刻触发 `vApplicationStackOverflowHook`;② 运行期用 `uxTaskGetStackHighWaterMark()` 看每个任务历史最小剩余栈,接近 0 就是危险信号。**栈溢出的现象通常是"随机跑飞/硬件错误/变量莫名被改"**——因为栈越界会踩到别的任务 TCB 或全局变量,每次踩到的东西不同,症状就随机。本项目配 2 档检查 + hook,跑飞时直接在 hook 里打印任务名进安全态。

**Q6:中断里能调什么?**

只能调带 `FromISR` 后缀的 API(`xQueueSendFromISR`、`xSemaphoreGiveFromISR`),不能调普通 `xQueueSend`——普通 API 会触发调度,而 ISR 不在任务上下文不能调度。需要切换任务时用 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)` 在 ISR 退出时做一次 PendSV。**本项目设计更激进:中断里连 FromISR 都不调**,只做 HAL 底层——DMA 完成中断只把 `RxState` 置 READY 就退出,所有业务逻辑都在任务级处理。这样 ISR 极短,抖动可控,也避开 ISR-任务通信的复杂度。

### 2.7 任务状态机与调度器启动(底层机制)

```
                 xTaskCreate                    调度器选择最高优先级
   ┌─────────┐  ──────────►  ┌─────────┐        ┌─────────┐
   │ 挂起     │               │ 就绪     │ ─────► │ 运行     │
   │(Suspend)│               │(Ready)  │ ◄───── │(Running)│
   └─────────┘               └─────────┘ 被抢占 └────┬────┘
        ▲                                            │ vTaskDelayUntil /
        │ vTaskResume                     等事件/锁  │ vTaskDelay / 等互斥锁
        └──────────────────────────────────── ◄─────▼
                      阻塞(Blocked)
```

- `xTaskCreate` 内部:从 heap_4 分配 TCB + 栈 → 初始化栈帧(伪造一次"被中断压栈"的现场,PC 指向任务函数)→ 挂入就绪链表。
- `vTaskStartScheduler`:创建 idle 任务 → 启动 SysTick(1ms)→ 上下文切换到最高优先级任务。本项目常驻任务 = 7 业务 + idle + (定时器服务,若启用)。
- 本项目无 Suspend/Resume 使用,状态流转全是"运行↔就绪↔阻塞"。

### 2.8 HAL 时基为什么换成 TIM(本项目真实配置,必考)

- FreeRTOS 需要 SysTick 做调度 tick;HAL 的 `HAL_Delay/超时` 默认也用 SysTick——**两者冲突**:移植后 HAL 拿到的 tick 被 FreeRTOS 接管,`HAL_Delay` 语义错乱。
- CubeMX 解法:HAL 时基改用一个普通 TIM(本项目 `stm32f1xx_hal_timebase_tim.c`,TIM4 类),1ms 中断喂 `HAL_IncTick()`;SysTick 专职 FreeRTOS。
- 回答口径:"我检查过 `HAL_GetTick()` 的来源是 TIM 时基中断,bootloader 里的超时判断不受 FreeRTOS 影响——bootloader 根本没跑 RTOS,但配置一致性好管理。"

### 2.9 内存布局与安全钩子

- **heap_4**:首次适配 + 相邻空闲块合并;`configTOTAL_HEAP_SIZE` 从 ZI 里静态划出(本机 ZI≈19.8KB,大头是它)。
- 任务栈全部来自这个堆 → 任务数和栈深直接决定 RAM 预算,这就是"栈怎么定"的 RAM 视角。
- 两个钩子都已具备:`vApplicationMallocFailedHook`(创建失败兜底)、栈溢出检测(`configCHECK_FOR_STACK_OVERFLOW`:方式一查栈边界,方式二查末尾 16 字节 pattern,溢出时进钩子可打印任务名)。

### 2.10 FreeRTOS 追问链(10 题)

以下按面试官追问顺序,答案为口头回答口径。

**Q1:怎么测每个任务 CPU 占用?**

标准做法是打开 `configGENERATE_RUN_TIME_STATS` 运行时统计,再调 `vTaskGetRunTimeStats()`,每个任务跑了多久一目了然。还有一个粗略的土办法:看 **idle 任务的权重**——idle 占比越高,系统越空闲,业务任务的整体占用就越低。

**Q2:同优先级怎么调度?**

FreeRTOS 对同优先级任务做**时间片轮转**,每个 tick 轮换一次。我的项目里 speed 和 motor 同为优先级 5,fusion 和 backflow 同为优先级 4,这两组都是靠时间片轮流跑的。

**Q3:中断里能给队列/任务发数据吗?**

可以,但必须用带 `FromISR` 后缀的专用 API,普通 API 在中断上下文里不安全。另外,如果这次发送唤醒了更高优先级的任务,退出中断前要调 `portYIELD_FROM_ISR(x)` 请求一次调度,否则任务切换会被推迟到下一个 tick 才发生。

**Q4:互斥锁和二值信号量区别?**

最关键的两点:互斥锁有**所有权**——谁拿的锁谁来放,并且带**优先级继承**,能防优先级反转;二值信号量这两样都没有,它的定位是事件同步或计数。一句话:保护数据用 mutex,同步事件用信号量,不能混用。

**Q5:任务通知(Task Notification)为什么快?**

因为它**直接写目标任务 TCB 里的 32 位值**,不经过队列这种内核对象,没有内核锁开销,官方数据是解除阻塞比二值信号量快约 45%。它适合一对一唤醒的场景,广播式通知就不合适了。

**Q6:`vTaskDelay(0)` 什么效果?**

它等于立即触发一次调度,主动让出 CPU,但自己仍然处于就绪态,马上就能参与下一轮调度。实际效果就是"礼貌地让高优先级任务先走一步"。

**Q7:怎么验证栈没定小?**

两个手段配合:`uxTaskGetStackHighWaterMark()` 看每个任务的**历史最小余量**,长期贴近 0 就说明该加栈了;再配栈溢出钩子,真溢出时进钩子可以打印任务名。另外 Keil 调试时也能静态观察 TCB 里的栈。

**Q8:这个项目为什么用 RTOS 不用前后台?**

因为我同时有 7 个不同周期的活动,还有 DHT11 这种毫秒级阻塞等待的外设。放前后台,主循环得靠一堆标志位和状态机拼出调度逻辑,复杂度爆炸,时序也没人保证。RTOS 的价值就在于**优先级和周期天然表达实时性**——`vTaskDelayUntil` 一写,时序就是调度器保证的。

**Q9:临界区里能调 `HAL_Delay` 吗?**

不能。临界区是关中断的,TIM 时基中断被屏蔽,tick 根本不走,而 `HAL_Delay` 恰恰是靠 tick 计数的,结果就是**永久死等**。所以临界区必须极短,只做纯内存操作,任何等待类调用都不能出现在里面。

**Q10:你的 10ms 按键周期怎么保证不抖?**

两层保证。一是用 `vTaskDelayUntil` 做**绝对对齐**,周期漂移不会累积;二是 key 任务的工作量极小——就 4 次 GPIO 读取,远小于 10ms 本身,每拍余量都很充足,抖动被压在 1 个 tick 以内。

### 2.11 上下文切换底层(PendSV,高频硬核题)

**MSP/PSP 双栈:** Cortex-M3 有两个栈指针。FreeRTOS 配置:**任务代码跑 PSP,内核/中断跑 MSP**——任务栈溢出不会砸到中断栈,中断响应也更可控。

**一次切换的完整过程:**

```
SysTick 中断(1ms)
  → xPortSysTickHandler():tick++ → 若需切换,pends PendSV
  → PendSV(最低优先级)真正干切换活:
      ① 硬件自动压栈 R0-R3,R12,LR,PC,xPSR 到当前任务 PSP 栈(8 个字)
      ② 软件压栈 R4-R11(8 个字)→ 共 16 字现场
      ③ 当前任务的 PSP 存进它的 TCB
      ④ 取下一个任务 TCB → 恢复它的 PSP → 弹 R4-R11 → BX LR(EXC_RETURN)
      ⑤ 硬件自动弹 R0-R3,R12,LR,PC,xPSR → 任务从断点继续跑
```

**两个必答"为什么":**

- **PendSV 为什么设最低优先级?** 保证切换动作等所有其他中断处理完才发生。若在 IRQ A 处理中途切换,A 返回时现场已换人。最低优先级 = "所有中断让完路才切换",这是 FreeRTOS 官方移植的标准做法。
- **xTaskCreate 为什么要"伪造栈帧"?** 任务第一次被调度时没有"被中断的现场",所以创建时手动在栈里摆好 R0-R3/PC/xPSR(PC 指向任务函数,xPSR bit24=1 即 Thumb),让 PendSV 的恢复代码以为它是"刚被切出去过的",弹栈即起跑。

### 2.12 任务间通信机制全景对比(选型题必考)

| 机制 | 语义 | 开销 | 本项目 |
|---|---|---|---|
| 全局变量 + 互斥锁 | 最新值快照 | 最小(锁操作) | ✅ g_state(见 2.3/2.4) |
| 队列 Queue | 消息流(逐条消费) | 中(拷贝 + 内核对象) | ✗(状态语义不需要) |
| 二值信号量 | 事件同步(ISR→任务) | 小 | ✗(DMA 完成走 HAL 状态位) |
| 计数信号量 | 资源池/事件计数 | 小 | ✗ |
| 互斥锁 Mutex | 资源独占 + 优先级继承 | 中 | ✅ state_lock |
| 事件组 EventGroup | 多条件与/或等待 | 中 | ✗(事件标志放 g_state) |
| 任务通知 TaskNotify | 一对一轻量唤醒 | 最小(直写 TCB) | ✗(演进项,见下) |

**标准答法:** "我的状态语义是'最新值'不是'事件流',所以共享结构+互斥锁最贴切。如果加按键长按通知 UI 或报警蜂鸣,我会用任务通知——不分配内核对象,直写目标 TCB 的 32 位值,官方数据:解除阻塞比二值信号量快约 45%,一对一场景最优。"

### 2.13 优先级反转完整案例(用本项目真实优先级讲)

设定:UI(优先级 1)、speed(5)、key(6),g_state 由互斥锁保护:

```
t0  UI 拿到锁,开始组装显示数据(持锁中)
t1  key 抢占,想拿锁 → 拿不到,阻塞(UI 还在持锁)
t2  speed 就绪 → 抢占 UI 跑起来(它不需要锁!)
    → 结果:key(6) 被 speed(5) 间接卡住 = 优先级反转
t3  (若无继承)speed 跑多久,key 就等多久——哪怕 UI 只差几微秒放锁
```

**互斥锁的优先级继承怎么救:** t1 时刻 UI 被临时提升到 6 → t2 speed 抢不过 UI → UI 几微秒内放锁 → key 拿锁,UI 恢复 1。反转窗口从"speed 整个执行期"压缩到"UI 持锁的那几微秒"。

**追问预备三连:**

- 继承是**临时的、自动的、只提一层**;不解决死锁(两把锁交叉持有)
- `configUSE_MUTEXES` 必须为 1 才有此行为
- 二值信号量没有继承 → **保护数据用 mutex,同步事件用信号量**,别混用

### 2.14 FreeRTOS 追问链·第二批(11~20)

以下按面试官追问顺序,答案为口头回答口径。

**Q11:SysTick 和 HAL tick 冲突怎么解?**

把 HAL 的时基从 SysTick 换到 TIM——TIM 产生 1ms 中断去喂 `HAL_IncTick()`,SysTick 让给 FreeRTOS 专职做 tick 源。这样**两边各用各的定时器**,互不干扰,具体配置见 2.8。

**Q12:任务栈里放什么?**

局部变量、函数调用的返回地址、参数,再加上 xTaskCreate 创建时**伪造的那份初始栈帧**。反过来讲,长生命周期的资源不要放栈上——栈帧随函数返回就没了,这类东西应该放全局区或者堆里。

**Q13:中断里能调 xTaskCreate 吗?**

API 层面不禁止,但有两层问题:一是 ISR 里只能用 FromISR 后缀的 API,`xTaskCreate` 不属于这一类;二是创建任务涉及**堆操作**,耗时不可控,违反"中断快进快出"的原则。正确做法是中断里只发通知,创建任务放到任务级去做。

**Q14:idle 任务干什么?**

三个职责:让 CPU 永远有事可做;回收 `vTaskDelete` 删除任务后遗留的资源(TCB 和栈);挂 idle hook,这是**低功耗处理的入口**。我的项目里 UI 任务优先级是 1,高于 idle,所以 idle 平时基本是纯空闲。

**Q15:怎么测中断响应延迟?**

GPIO 翻转加示波器:外部给一个信号沿,ISR 里翻转另一个 GPIO,两个沿的时间差就是延迟。要注意**临界区越长,延迟越大**——比如 DHT11 关中断不到 25ms,这段窗口里所有中断都被挡住,这就是代价,面试时能主动说出这个代价就是加分。

**Q16:调度抖动(周期不稳)有什么危害?**

对控制环是致命的:PID 的离散系数是按采样周期算的,采样周期一漂移,实际控制参数就变了,极端情况下**闭环失稳**。我的对策是 `vTaskDelayUntil` 绝对对齐,加上控制类任务保持高优先级、短工作量,把 key/speed 的抖动压进 1 个 tick 以内。

**Q17:FreeRTOS 的堆和 C 库堆是同一个吗?**

不是。heap_4 实际是 SRAM 里的一块静态数组 `ucHeap`,任务 TCB、栈、队列都从这里分配;C 库的 malloc 是另一套独立体系。我的项目 APP 和 bootloader 都不用 malloc,所以 C 库堆根本不存在,只有 FreeRTOS 这一份。

**Q18:两个任务同时写 g_state.pwm_duty 会怎样?**

不加锁就是经典的**丢失更新**:后写的覆盖先写的,先写那条路径的控制意图凭空消失。我的项目用两层防御:模式互斥保证手动/自动只有一条控制路径生效,写入时持互斥锁——任何时刻只有一条路径能写这个字段。

**Q19:为什么不把所有逻辑塞一个任务?**

塞进一个任务就退化成前后台了:周期要靠软件计数器凑,优先级彻底失效,任何一段代码阻塞都会拖累全局。拆成 7 个任务之后,周期和优先级交给调度器保证,**锁的粒度也小**,每个锁只保护自己那部分状态。

**Q20:优先级数字越大越高还是越小越高?**

这是高频陷阱题,两套体系方向相反:FreeRTOS 里**数字越大越高**(0 到 configMAX_PRIORITIES-1);Cortex-M 的 NVIC 恰好相反,**数字越大越低**。配任务和配中断用的不是同一把尺子,千万别背反。

## 3. PID 深度讲解(重点)

### 3.1 控制系统框图

```
                 目标转速                     ┌──────────┐  占空比‰   ┌─────────┐
 档位开关 ──►  setpoint ──►(+)── e(k) ──►  │ 位置式PID  │── out ──► │ 前馈基准 │──► PWM
 (190/220RPM)             (-)▲              │ Kp=2.0    │            │ 400‰    │      │
                             │              │ Ki=0.05   │            └─────────┘      ▼
                             │              │ Kd=0      │                        ┌─────────┐
                             │              └──────────┘                        │ TIM1 PWM│
                             │                                                  │ →TB6612 │→ 风机
                             │              ┌──────────┐                        └─────────┘
                             └──────────────│ 编码器测速│◄────── 风机轴 ─────────────┘
                               实际转速 RPM │ TIM3×4倍频│   50ms 采样
                                            └──────────┘
```

框图语言版:**前馈 + 反馈复合控制**。前馈(开环基准 400‰)负责"大概对",PID(闭环)负责"精确补"。

**信号流向逐段讲解(什么导致什么,什么驱动什么):**

把框图看成一条从左到右的因果链,一共六环,前一环直接导致后一环:

**① 档位 → 目标转速(用户需求驱动控制目标)**
档位开关被按下,key 任务把档位写进 `g_state.target_rpm`——低档 190RPM、高档 220RPM。**人的操作是整条链路的总源头**,它不直接碰电机,只决定"我要多少转速"。

**② 目标 − 实际 → 误差 e(k)(减法导致误差)**
speed 任务每 50ms 取一次 `e(k) = target_rpm - actual_rpm`。这个减法点是闭环的核心:**实际转速低于目标,e 为正,系统就要加力;高于目标,e 为负,就要减力**。误差的正负直接决定了后面 PID 输出的方向。

**③ 误差 → PID 输出(误差驱动修正量)**
P/I/D 三项把误差换算成一个整数修正量 `out`(单位千分比):
- **P 项**:`Kp·e`,误差当下有多大就立刻修多少(Kp=2,即每差 1RPM 出 2‰);
- **I 项**:`Ki·Σe`,误差持续存在就一直累加,专治"差一点点却永远到不了"的静差;
- **D 项**:本项目 Kd=0,主动关掉——转速测量噪声会被微分项放大,不用反而更稳。

**④ PID 修正 + 前馈基准 → 总占空比(基准负责"大方向",PID 负责"微调")**
`pwm_duty = 400 + out`。前馈 400‰ 是**实测出来的**:风机在目标转速附近,开环给 400‰ 占空比基本就能转在工作点。PID 的 `out` 只是在这个基准上做 ±几百的修正。**为什么必须有前馈**:如果让 PID 从 0 开始单独干,刚启动误差 190 → P 项就 380‰,瞬间顶到限幅,响应又冲又容易饱和;加了 400‰ 基准,起点就在工作点附近,PID 只需小幅修正,平稳得多。

**⑤ 占空比 → TIM1 PWM → TB6612 → 风机(数值驱动硬件)**
motor 任务 50ms 读一次 `g_state.pwm_duty` 写进 TIM1 的 CCR 寄存器,**占空比这个数字导致 PWM 波形改变** → TB6612 电机驱动根据 PWM 改变输出电压 → 风机转速随之改变。这一环是"软件数值"变成"物理运动"的转换点。

**⑥ 风机转动 → 编码器 → 实际转速(物理量被测量回来)**
风机轴带动编码器旋转,编码器输出脉冲进 TIM3,4 倍频后由 speed 任务 50ms 数一次脉冲换算成 RPM。**物理转速被重新测回数字量**,送回第 ② 环的减法点——这就是"反馈",也是"闭环"这个名字的由来:信号从输出端绕了一圈回到输入端。

**一句话因果总结:**

> **档位决定目标 → 目标和实际的偏差驱动 PID → PID 的修正叠加在前馈基准上 → 总占空比驱动 PWM → PWM 驱动电机 → 电机转速被编码器测回来再和目标比较**——一圈一圈收敛,直到 `actual ≈ target`,此时 e≈0,PID 不再出力,系统稳定在目标转速上。

### 3.2 位置式 PID 公式与代码逐行对应

位置式(全量式):

```
u(k) = Kp·e(k) + Ki·Σe(i) + Kd·[e(k) − e(k−1)]
```

代码([pid.c](../RTOS%20%20YJ/APP/pid.c)):

```c
int32_t pid_update(pid_t *pid, int32_t setpoint, int32_t measurement)
{
    int32_t error = setpoint - measurement;   /* e(k) = 目标 − 实际 */
    float p, d;
    int32_t out;

    pid->integral += (float)error;            /* 累积 Σe */
    /* 积分限幅:抗积分饱和 */
    if(pid->integral > (float)pid->out_max)  pid->integral = (float)pid->out_max;
    if(pid->integral < (float)pid->out_min)  pid->integral = (float)pid->out_min;

    p = pid->kp * (float)error;                          /* 比例项 */
    d = pid->kd * (float)(error - pid->last_error);      /* 微分项 */

    out = (int32_t)(p + pid->ki * pid->integral + d);    /* 合成 */

    if (out > pid->out_max) out = pid->out_max;          /* 输出限幅 */
    if (out < pid->out_min) out = pid->out_min;

    pid->last_error = error;                             /* 保存本次偏差给下次微分用 */
    return out;
}
```

**参数与结构(真实值):** `PID_KP=2.0, PID_KI=0.05, PID_KD=0.0`,积分限幅 ±300,输出限幅 ±300,采样周期 50ms。

### 3.3 三个必讲的设计点

**① 前馈基准 400‰(`s_pid_base = 400`):**

```c
int32_t pwm = (int32_t)s_pid_base + out;   /* 前馈基准 + PID 修正 */
```

> 风机在正常工作区大约需要 40% 占空比。如果让 PID 从 0 开始"扛"全部输出,积分要累积很久(启动慢、超调大)。前馈把开环工作点先顶上,PID 只负责修正 ±300‰ 内的偏差——响应快、积分负担小、超调小。这是**前馈+反馈复合控制**思想。

**② 积分限幅 = 抗积分饱和(anti-windup):**

> 现象:启动或大偏差时,输出长时间顶在上限,Pure 积分累积到很大(饱和);之后转速到达目标、误差反号,积分需要"泄放"很久才能让输出离开上限 → 严重超调。
> 对策:积分器本身限幅(±300),输出到不了的地方积分也不许去。
> **如实说:** `app_config.h` 里定义过 `PID_INTEGRAL_MAX 500`,但 `tasks_init` 实际传给 `pid_init` 的是 `±PID_OUT_MAX(300)`,即当前积分限幅与输出限幅同幅——这是我刻意简化的做法,两个限幅解耦是更完善的形式。

**③ Kd = 0,为什么转速环不用微分:**

> 编码器 50ms 窗口计数只有个位数计数,量化噪声大;微分对噪声放大(Kd × 噪声差分),D 项抖动比它抑制的超调更有害。风机是大惯性执行机构(机械时间常数 >> 50ms),P+I 已经够稳。工业上"PI 调速 + 不加 D"很常见。

### 3.4 测速反馈与分辨率(展示深度)

```c
cpr = ENCODER_PPR * 4 * GEAR_RATIO;   /* 13 线 × 4 倍频 × 减速比 1 = 52 计数/转 */
rpm  = delta × 60000 / (dt_ms × cpr); /* 50ms 窗口换算每分钟转数 */
```

**① 硬件链路:TIM3 编码器模式 TI12 双通道四倍频**

编码器本体每转只输出 13 个脉冲(13 PPR),但 A、B 两相相位差 90°,TIM3 的 TI12 模式在两相的每个跳变沿(上升/下降 × A/B)都计数一次,于是硬件层面把分辨率放大 4 倍:**13 × 4 = 52 计数/转**。这是第一个"不换编码器也能提分辨率"的手段——四倍频是定时器外设白送的,不占 CPU。

**② 量化分析:低速下一个窗口只有 8 个计数(能算出这个数就赢过 90% 候选人)**

低档目标 190 RPM,采样窗口 50ms,一个窗口里的计数数:

```
delta = 190 转/分 × (50/60000)分 × 52 计数/转 ≈ 8.2 个计数
```

问题在于**定时器的计数是离散的**——只有 8、9 这样的整数,没有 8.2。真实物理转速哪怕一点没变,每个窗口脉冲到达时刻的微小抖动,也会让读数在 8 和 9 之间跳。±1 个计数的量化误差相对于 8.2 个计数:

```
1 / 8.2 ≈ ±12% 转速测量噪声
```

也就是说 190 RPM 的真实转速,测回来可能显示 167 或 213——**这个噪声不是电路干扰,是低速低分辨率的数学必然**,滤波只能缓解,不能消除。速度越高计数越多,噪声占比越小(220 RPM 时约 9.5 个,±10.5%),所以这个问题专门咬低速段。

**③ 噪声直接导致的设计决策:Kd = 0**

微分项的本质是 `Kd·(e(k) − e(k−1))/dt`——**对误差做差分,等价于高通滤波,会放大高频噪声**。转速测量本身带着 ±12% 的抖动,相邻两次采样的误差差分会在正负之间乱跳,乘出来的 D 项就是一串随机脉冲叠加到 PWM 上,表现为电机嗡嗡抖动。我在调参时试过 Kd=0.05 量级,转速数字明显抖动、电机有可感知的抖振,对控制质量没有任何改善,最终置 0。**这不是照教科书省略,是实测后的取舍**。

**④ 三条降噪路线及各自代价(演进方向,面试主动讲)**

| 方案 | 效果 | 代价 |
|---|---|---|
| 滑动均值滤波(对 N 次 delta 求平均) | ±1 误差摊薄到 1/N,立刻见效 | 引入 N/2 个窗口的相位滞后,速度变化时反馈变慢;N 大了影响闭环动态 |
| 换高线数编码器(如 500 PPR → 2000 cpr) | 同样 50ms 窗口计数从 8 涨到 317,量化噪声降到 0.3% | 硬件成本 + 最高脉冲频率上升,要重新核算定时器输入频率上限 |
| 加大采样窗口(50ms→100ms) | 计数翻倍,噪声减半 | 采样率下降,控制环变慢;与"远小于电机机电常数"的采样原则冲突,有上限 |

工程上通常**先上软件滤波(零成本)、精度要求高的产品再换硬件**;加大窗口是最便宜但受限于控制动态,只能小幅调。本项目当前实际落地的是"4 倍频 + Kd=0"两条,滑动均值是预留的下一步。

**⑤ 读 delta 即清零 CNT:一个省掉整套溢出处理的设计**

TIM3 的 CNT 是 **16 位计数器(0~65535)**,常规做法要处理溢出:开更新中断维护一个高位累加值,或按两次读数关系推算绕回,代码复杂还容易错。本项目的做法见 [encoder.c](../RTOS%20%20YJ/BSP/encoder.c):

```c
int32_t encoder_get_delta(void)
{
    int32_t c = (int32_t)__HAL_TIM_GET_COUNTER(&htim3);  /* 读 */
    __HAL_TIM_SET_COUNTER(&htim3, 0);                    /* 读完即清零 */
    return c;                                            /* 返回的就是这一窗口的增量 */
}
```

因为采样严格 50ms 一次、低速下窗口内只有几个计数,**每个窗口结束时把 CNT 归零,CNT 里的瞬时值天然就是"本窗口增量"**,16 位空间绰绰有余,溢出在物理上不可能发生(8 个计数离 65535 差四个数量级),于是溢出中断、高位累加、符号修正全部不需要。清零同时天然保留方向:反转时 CNT 向下减,读数即为负增量。

*进阶补充(被追到底再讲):读和清零是两条指令,中间若恰好来一个编码器边沿会丢 1 个计数。本项目 190RPM 时脉冲间隔约 6ms,指令窗口几十 ns,概率可忽略;高速场景更严谨的做法是"溢出中断累加 + 读 CNT 合成 32 位"而不是清零。*

**一句话总结(面试收尾用):**

> 低速段 50ms 窗口只拿到约 8 个计数,±1 离散量化带来约 12% 测速噪声,所以 Kd 必须关、必要时上滑动均值或换高 PPR 编码器;读窗口即清零 CNT,用"每窗口增量远小于 65535"这个物理事实,换来了整套溢出处理逻辑的消除——**测量端的分辨率约束,一路传导到了 PID 结构和代码实现**。

### 3.5 参数怎么调的(面试必问"调参过程")

> 方法:**先 P 后 I 再 D,阶跃观察法。**
> 1. Ki=Kd=0,从小到大加 Kp:目标 190→220 RPM 阶跃,看响应。Kp 太小爬得慢、稳态误差大;太大振荡。本机 Kp≈2.0(每 100RPM 误差出 200‰ 占空比修正)时响应快且不振荡。
> 2. 加 Ki 消除稳态误差(风机负载下 P 控制必有静差):Ki 从 0.01 起,太小收敛慢、太大来回摆;0.05 时 1~2 秒内稳态误差归零且不反复超调。同时配积分限幅,否则启动段饱和超调。
> 3. Kd 试过 0.05 量级:转速数字明显抖动(测速噪声被微分放大),对控制质量没有可感知改善,最终置 0。
> 4. Proteus 仿真里同样流程先粗调,上机只微调。

| 位置式 vs 增量式? | 位置式输出全量、要积分限幅;增量式 Δu=KpΔe+Ki e+Kd ΔΔe,输出增量、天然无积分饱和、适合执行器是步进/累积型。风机 PWM 是全量型,选位置式 |
| 积分饱和是什么? | 见 3.3②;后果是超调和恢复迟钝;对策:积分限幅/抗饱和/积分分离 |
| 为什么用 float? | F103 无 FPU!float 是软件模拟(慢但 50ms 周期下无所谓);更优化做法:全整数 PID(乘 1000 定点),fusion.c 就是这么做的 |
| 采样周期怎么定? | 远小于被控对象时间常数(电机机电常数几百 ms),50ms 足够快又给编码器足够的计数窗口 |
| PID 输出直驱什么? | 输出 ±300‰ 叠加前馈 400‰ → 限幅 0~1000‰ → `CCR = duty×(ARR+1)/1000` 写 TIM1 |

### 3.7 手算一轮 PID(面试官真会让算,10 分钟能练熟)

**设定:** 目标转速 190,当前实际 180,上轮误差 15,积分累积 20,`KP=2.0, KI=0.05, KD=0,前馈 400‰`

```
e(k)      = 190 − 180 = 10
P         = KP × e(k)           = 2.0 × 10    = 20
积分更新   = 20 + e(k)           = 30          (|30| < 300,不触发积分限幅)
I         = KI × Σe             = 0.05 × 30   = 1.5
D         = KD × (e(k) − e(k-1))= 0 × (−5)    = 0
PID输出    = P + I + D           = 21.5 → 截断为 21
PWM       = 前馈 400 + 21        = 421‰        (0~1000 内,不截断)
```

**要能说清的三件事:** ① 误差单位是 RPM,输出单位是 PWM 千分比,KP=2.0 意味着每 1 RPM 偏差修正 2‰ 占空比;② 积分限幅判断发生在累积之后、使用之前;③ 结果取整后叠加前馈,最后还有一次 0~1000 输出限幅——**两级限幅是两道独立保险**。

### 3.8 现象 → 诊断 → 对策(调参实战表)

| 现象 | 诊断 | 对策 |
|---|---|---|
| 转速稳定但到不了目标 | 纯 P 有稳态误差 / Ki 太小 | 加大 Ki(本项目 0.05 消差) |
| 到达目标后来回摆 | Ki 过大,积分来回充放电 / 积分饱和 | 减 Ki、确认积分限幅生效 |
| 目标阶跃时严重冲过头 | 无前馈、PID 从 0 爬 / Kp 过大 | 加前馈基准(400‰ 的来历)、减 Kp |
| 转速数字疯狂抖动 | 测速量化噪声被 D 放大 / Kp 过大 | Kd 置 0、对测量值滑动平均 |
| 启动到目标耗时长 | Kp 小且无前馈 | 提前馈,让 PID 只管偏差 |
| 负载突变恢复慢 | 积分作用弱 | 适当加大 Ki 或缩短采样周期 |

**调参顺序话术:** "先 P 后 I 再 D。P 从小到大调到临界振荡再回退 30~50%;I 消除稳态误差,配合积分限幅防饱和;D 看噪声水平,转速环噪声大所以 Kd=0。每一步都用阶跃响应观察——这是齐格勒-尼科尔斯思想的工程简化版。"

### 3.9 位置式 vs 增量式(对比表,必考)

| 维度 | 位置式(本项目) | 增量式 |
|---|---|---|
| 输出 | 全量 u(k),直接可执行 | 增量 Δu(k),需累加到执行器 |
| 积分饱和 | 会发生,必须限幅 | 天然无累加项,不易饱和 |
| 积分截断影响 | 输出突跳风险小 | Δu 直接受限幅影响 |
| 适合执行器 | PWM/阀位等**绝对位置型** | 步进电机/需累积驱动的**增量型** |
| 手动/自动切换 | 需无扰切换处理 | 天然平滑(从当前值继续加增量) |
| 本项目选择理由 | 风机 PWM 就是绝对占空比,直接输出最自然 | — |

### 3.10 改进变体(说得出名字 + 一句话原理即可)

- **积分分离**:误差大于阈值时暂停积分(大偏差只 P+D 快速逼近,进带内再开 I),进一步压超调
- **不完全微分**:D 项串一阶低通,抑制高频噪声放大
- **微分先行**:对测量值而非误差微分,避免目标突变时 D 项打满
- **反算式抗饱和(back-calculation)**:输出限幅发生时按比例回吐积分,比硬截断平滑
- 一句话收尾:"我的场景是二阶不到的机电对象 + 噪声大的测速,PI+前馈已经满足,这些变体是知道何时该上的工具。"

### 3.11 float 开销与定点化(展示优化意识)

- F103 无 FPU,float 乘加是软件库调用(几十周期);50ms 周期、一次十几条浮点运算,占空比完全可以忽略——**先说"为什么不优化",再说"要优化怎么做"**,这是工程判断力。
- 定点化方案(与 fusion.c 同风格):

```c
/* KP=2.0 → KPX=2000;KI=0.05 → KIX=50;结果右移 1000 */
p   = (int32_t)((int64_t)KPX * e) / 1000;
integ += e;  integ = clamp(integ, INTEG_MIN*1000, INTEG_MAX*1000);
i   = (int32_t)((int64_t)KIX * integ) / 1000;
out = p + i;
```

### 3.12 PID 追问链(8 题)

以下按面试官追问顺序,答案为口头回答口径。

**Q1:你的 PID 输入输出是什么量纲?**

输入是转速误差,单位 RPM;输出是 PWM 占空比,用千分比表示。KP 取 2,含义很具体:**每 1 RPM 的误差,输出修正 2‰ 的占空比**。整个控制器从输入到输出的量纲是贯穿的,每一步都说得清。

**Q2:为什么 50ms 采样?**

两个原因的交汇点。电机的机电时间常数是几百毫秒量级,50ms 采样**远快于对象响应**,离散化失真可以忽略;同时 50ms 的窗口也给编码器攒够了计数,转速分辨率才够用——采样再快,计数太少,测速本身就是噪声了(详见 3.4)。

**Q3:积分限幅和输出限幅为什么两个都要?**

因为它们限的对象不同。积分限幅防的是"**历史累积过深**"——积分饱和会让系统超调、恢复迟钝;输出限幅防的是"**本次突跳**"——单拍算出再大的值,执行器也只能收 0~1000。一个管历史,一个管当前,互不替代。

**Q4:前馈值怎么定?**

实测来的:风机在目标转速附近的开环占空比大约 40%,也就是 400‰,拿它当前馈。前馈负责**粗定工作点**,PID 负责在附近精修,不需要特别准——差的那部分由积分补上。

**Q5:PID 参数换硬件要重调吗?**

必须重调。KP 的量纲里含执行机构增益,风机换了、驱动换了、供电电压变了,同样 1 RPM 误差需要的占空比修正就不一样。所以我把参数做成**可配置的**,全放在 `app_config.h` 的宏里,换硬件改宏重编译就行。

**Q6:自动模式和手动模式两个控制路径怎么不打架?**

靠**模式互斥**。手动模式下,fusion 的输出被忽略;自动模式下,speed 任务的 PID 根本不执行。模式判断放在持锁区内做,保证任何时刻只有一条路径能写 pwm_duty,不会出现两个来源交替写同一个字段。

**Q7:测速有噪声怎么办?**

多管齐下:Kd 直接置 0,从源头回避——微分会把测速噪声放大,这是最狠的一招;编码器 4 倍频把计数做上去,提高分辨率;必要时对 delta 做**滑动平均**;最后还有限幅兜底。层层设防,不让噪声一路走到执行器。

**Q8:如果转速环震荡了怎么定位?**

按顺序排查。先降 Kp,震荡消失就说明是比例项太激进;再查采样周期有没有被调度抖动拉长——离散控制的假设被破坏,是会失稳的;最后看执行机构有没有死区或饱和。这题其实把 RTOS 章和控制理论串起来了:调度抖动不只是体验问题,是稳定性问题。

### 3.13 被控对象视角:风机是个什么对象(控制专业面试官会问)

- 风机 + 驱动 ≈ **一阶惯性环节**:`G(s) = K/(τs+1)`,τ 是机电时间常数(阶跃后转速爬到 63% 目标的时间,本对象数百 ms 级)。
- **PI 就能镇定一阶对象**:P 提供响应刚度,I 消除负载静差;D 对二阶以上欠阻尼对象才有明显收益——这是 Kd=0 的理论支撑。
- **采样定理角度**:50ms 采样 vs 几百 ms 时间常数 → 采样频率远高于对象带宽 10 倍以上,离散化失真可忽略。经验法则:**采样周期 ≤ τ/10**。
- **纯延迟与离散失稳**(进阶):采样过慢时相位滞后累积,闭环发散,现象就是"越调越摆"——这正是 3.12-8 "调度抖动导致失稳"的理论根源,把 RTOS 章和 PID 章串起来了。

### 3.14 手算第二轮:扰动恢复(积分怎么"泄放")

**场景:** 稳态运行中突加负载,转速 190→170;稳态时积分已累积 Σe=10;KP=2.0, KI=0.05, KD=0,前馈 400‰

```
稳态时:  e=0 → P=0,I=0.05×10=0.5,PWM≈400‰(积分在悄悄补着负载)
突加负载:e(k) = 190 − 170 = 20
P        = 2.0 × 20 = 40            ← 立即出力(比例的功劳)
积分更新  = 10 + 20 = 30 → I = 1.5  ← 慢慢追加(积分的功劳)
PID输出   = 41.5 → 截断 41 → PWM = 441‰
```

**要讲出的动态分工:** "P 是'现挂'——当拍误差立即响应;I 是'记账'——把历史欠账补上;D 是'预判'——看误差变化趋势。负载恢复过程中误差逐渐缩小,P 项跟着缩,已累积的积分继续托底输出,直到转速回到 190、e=0 后由积分独自抵消负载——这就是为什么没有积分就永远回不到无静差。"

### 3.15 PID 追问链·第二批(9~16)

以下按面试官追问顺序,答案为口头回答口径。

**Q9:误差单位 RPM、输出单位 ‰,量纲差这么远没关系?**

没关系,增益的职责本来就是**量纲换算**:KP=2 就是把 1 RPM 的误差换算成 2‰ 的占空比修正。但换个风机,对象增益变了,KP 就得重调——所以我坚持参数必须可配置,放在 `app_config.h` 的宏里。

**Q10:积分限幅 ±300 和输出限幅相同,合理吗?**

能跑,但确实不是最优。积分限幅应该独立设置,经验上常取输出限幅的 0.7~1 倍,给积分留"余量"又不至于病态。如实说,两处限幅同值是我现在的简化,把两个限幅**解耦**列在我的改进项里(见 3.3②)。主动承认比被面试官戳穿强。

**Q11:输出为什么还要再限幅 0~1000?**

按当前参数算,前馈 400 加上 PID 的 ±300,最大也就 700,理论上碰不到边界。但这个限幅是**防御性编程**:万一以后前馈调大,没有这道闸门输出就冲出去了。限幅的意义就在于不依赖当前参数组合依然安全。

**Q12:PID 每周期几次浮点运算?**

很少:P、I 各一次乘,D 一次减,再加加法合成,一共**两乘一减**。F103 没有 FPU,浮点是软件模拟,一次乘法几十个周期——但放在 50ms 的控制周期里完全可忽略(3.11 算过这笔账)。

**Q13:换成增量式要动哪些代码?**

改动清单:输出改成 Δu 累加、删掉积分变量、限幅移到 Δu 上。还有一个容易漏的坑:要处理"PID 停用期间执行器状态"的问题——停用再启用时,增量式的累积起点是错乱的;**位置式没这个坑**,这也是我当初选位置式的原因之一。

**Q14:目标值阶跃(190→220)响应什么样?**

P 项打头阵:2.0 乘以 30 RPM 的误差,立即输出 60‰ 出力;因为前馈已经把工作点顶在目标附近,基本不会有大超调。如果阶跃瞬间 D 项抖动明显,标准改进是**微分先行**——对测量值微分而不是对误差微分,目标突变就不会直接打进微分项。

**Q15:编码器坏了(反馈恒 0)会怎样?**

误差恒定在 190,P 项算出 380,直接顶到输出限幅 300;PWM 顶到 700‰ 全速转,积分饱和被限幅按住,**不会失控发散**。但更好的做法是加反馈有效性检查——检测到反馈异常就切断闭环进安全态,这和传感器降级是同一个思想,列在我的改进项里。

**Q16:PID 采样频率和 PWM 载波频率什么关系?**

两个完全独立的频率:PID 采样是 20Hz(50ms 一拍),PWM 载波是 TIM1 输出的几十 kHz。约束是**采样必须远低于载波**——否则一个控制周期内平均不到有效占空比,闭环测到的就是"噪声"。

## 4. 传感器融合与业务逻辑

### 4.1 加权融合算法(fusion.c)

```
f_T = clamp((T − 20.0℃) / 20.0℃ , 0, 1)
f_H = clamp((H − 40%)   / 40%,   0, 1)
f_G = clamp((G − 80ppm) / 220ppm,0, 1)
F   = 0.2·f_T + 0.2·f_H + 0.6·f_G          ← 烟气为主导
PWM = 1% + F × 99%
```

- **min-max 归一化 + 去基线**:室温/常湿贡献为 0,只有"超出日常背景"的部分才驱动风力。
- **全整数实现**(面试亮点):避免 F103 无 FPU 的 float 开销——权重以 1/10 为单位(`W_T=2, W_H=2, W_G=6`),可信度放大 1000 倍(`F1000`),纯移位乘除:

```c
F1000 = (FUSION_W_T * fT) / RANGE_TEMP +
        (FUSION_W_H * fH) / RANGE_HUMID +
        (FUSION_W_G * fG) / RANGE_GAS;
pwm = PWM_BASE_PERMILLE + (F1000 * (PWM_PERMILLE_MAX - PWM_BASE_PERMILLE)) / 1000;
```

- 权重 0.6 给烟气的理由:油烟机的本质是排烟,温/湿度是辅助判据(蒸汽也会触烟感)。

### 4.2 自动模式三态状态机(state_machine.c)

```
AUTO_STANDBY(待机,PWM=0)
   │ 进入自动模式
   ▼
AUTO_MIN_RUN(最小运转 300‰,最长 60s)──60s 无烹饪事件──► STANDBY
   │ 检测到烹饪事件(烟气 > 80+220×? 阈值)
   ▼
AUTO_ADJUST(动态调节,输出融合 PWM)
   │ 事件消失 → 启动 10s 退出计时;期间再检测到事件则计时复位
   ▼ (10s 到)→ STANDBY
```

- "最小运转"考虑电机启动/低速区效率差,进了自动模式先给个最低工作点,而不是 0。
- **10s 延时退出**:炒菜结束烟气不会立刻散,避免风机"人走茶就凉"。

### 4.3 防倒灌检测(backflow.c,迟滞回差)

```c
未激活:  gas > 150ppm  → 激活
已激活:  gas < 120ppm  → 释放
(120~150ppm 之间:保持原状态)
```

> 迟滞(hysteresis)防抖:公共烟道串味浓度在阈值附近波动,单阈值会造成继电器频繁通断(抖振)。两个阈值形成 30ppm 死区,状态只在穿越两侧时改变——和温控器、施密特触发器同一个思想。

### 4.4 DHT11 采集的三个工程细节

1. **单总线 µs 时序**:用 DWT 周期计数器(CYCCNT)做精确微秒延时(`delay_us`),比 NOP 循环准。
2. **临界区保护**:整个位读取期间 `taskENTER_CRITICAL()`(关中断),防 1ms RTOS tick 打断时序;代价是期间响应延迟,但 <25ms 可接受。
3. **失败降级**:读取失败温湿度清 0,融合端基线归一化后贡献自动为 0——**传感器故障不会导致风机乱转**。
4. GPIO 用**开漏输出+外部上拉**,方便输入/输出方向切换。

### 4.5 MQ135 烟气采集

- ADC1 轮询采样,8 次均值滤波(简单有效抑制随机噪声),上电先 `HAL_ADCEx_Calibration_Start()` 校准。
- 线性映射 `ppm = raw × 400 / 4096` ——**如实承认是简化**:MQ135 真实灵敏度曲线非线性且需温湿度补偿,精确测量要标定/Rs-Ro 曲线。本项目用它做趋势与阈值判断,线性近似够用。这句话面试官听了会舒服,说明你知道自己简化在哪。

## 5B. HardFault 与疑难问题定位(呼应 1.9 排查表)

> 面试官最爱问"你项目里遇到最难的问题怎么定位的"——这一章就是标准答案的素材库。

### 5B.1 HardFault 定位标准流程(五步,Keil 在线调试)

```
① 停住看 LR(EXC_RETURN):
     bit2 = 0 → 出错前用 MSP(中断/内核栈)
     bit2 = 1 → 出错前用 PSP(任务栈,RTOS 下先查任务)
② 按对应 SP 找硬件压栈帧(8 个字):
     SP+0x00 R0 | +0x04 R1 | +0x08 R2 | +0x0C R3
     +0x10 R12 | +0x14 LR | +0x18 PC(出错位置!)| +0x1C xPSR
③ 读故障状态寄存器定位错误类型:
     SCB->CFSR(0xE000ED28)/HFSR(0xE000ED2C):
       UNDEFINSTR  → 跳到非指令区(典型:向量表/跳转错误)
       INVSTATE    → PC 给了 bit0=0 的地址(Thumb 位丢失,正是跳转五步防的)
       PRECISERR   → 精确总线错,出错地址在 BFAR(0xE000ED38)
④ 拿压栈 PC 值对照 .map 文件 → 定位到函数 + 偏移
⑤ 回查代码:野指针/数组越界/栈溢出/未初始化
```

### 5B.2 嵌入式常见跑飞原因分类(按命中率排序)

| 原因 | 典型现象 | 验证手段 |
|---|---|---|
| 栈溢出 | 随机跑飞;改个无关代码就复现/消失 | `uxTaskGetStackHighWaterMark`、`configCHECK_FOR_STACK_OVERFLOW=2`(栈底 16 字节 pattern)、临时加大栈验证 |
| 野指针/数组越界 | 稳定复现,PC 落在奇怪地址 | CFSR 精确地址 + map 对照 |
| 向量表错(VTOR/链接基址) | 一开中断就死;跳转后跑飞 | 调试读 VTOR 寄存器 vs 实际向量表位置 |
| 外设未开时钟就使用 | 读写寄存器无响应 | 检查 `__HAL_RCC_*_CLK_ENABLE` |
| printf 半主机依赖 | 一用 printf 就死 | 勾 MicroLIB、重定向 fputc |
| 缺 volatile | -O0 正常 -O2 异常 | 检查 ISR 共享变量/硬件寄存器轮询(见第 9 章第 1 题) |

### 5B.3 本项目真实踩坑(讲出来就是调试经历)

1. **APP 链接基址没改,覆盖 bootloader** → 烧完 APP 后 bootloader 没了,只能 SWD 救砖。定位:看 map 文件 `LR_IROM1` 基址 + hex 首记录地址。教训:**向量表偏移(VECT_TAB_OFFSET)和链接地址(Keil IROM/OCR_RVCT4)是两个独立配置,必须一起改**——这是我项目里最有含金量的一次踩坑。
2. **hex 基址误判**:ELA 记录 `:02000004 0800` 只给高 16 位,要与数据记录偏移相加才是真地址(0x0800 + 0x4000 = 0x08004000)——工具链知识不扎实会冤枉自己的代码。
3. **CRC 尾字节丢失**:bootloader 写最后一块 + flush 的几 ms 空窗里,上位机紧跟的 CRC 尾丢进 ORE → 整包校验失败。定位:对照 1.2 的 NDTR≠0 检测 + 串口时序分析;对策:上位机发 CRC 前延时 20ms(见 1.6)。

## 6. 高频追问总表(面试前一天过一遍,答案为口头回答口径)

### Bootloader 类

1. **为什么 APP 要 0x08004000?** 三个约束共同决定的。bootloader 占前 16KB,APP 只能从它后面开始;F1 中容量产品页大小是 2KB,0x4000 正好落在页边界上;同时 VTOR 的对齐要求(向量表大小向上取 2 的幂、至少 512B)也一并满足。
2. **向量表偏移改哪里?** 两处,缺一不可:`system_stm32f1xx.c` 里打开 `USER_VECT_TAB_ADDRESS` 并设 `VECT_TAB_OFFSET 0x4000`;**以及 Keil Target 选项里 IROM 起始改 0x8004000、大小 0x7C000**。只改向量表不改链接地址,代码还是编到 0x08000000——这是最容易踩的坑,我自己踩过。
3. **升级到一半掉电?** 不会变砖。bootloader 前 16KB 任何代码路径都碰不到,掉电伤不到它;重启后 APP 区是脏的,镜像校验不通过,bootloader 拒绝跳转、自动留在升级模式,重传一次就好。
4. **为什么不把 bootloader 也擦了?** 因为 bootloader 本身就是"救援通道"——把它擦了,串口 IAP 就没了载体,只能拆机上 SWD 才能救回来。
5. **`HAL_GetTick()` 溢出?** 不用担心。无符号减法天然带模运算特性,就算 49.7 天回绕,`(now - t0)` 的差值依然正确,超时判断不受影响。
6. **DMA Normal vs Circular?** 看语义选。Normal 收满即停,适合"收固定长度一块、处理一块"的场景,我的 bootloader 就是它;Circular 连续循环覆盖,适合 APP 侧那种长度不确定的串口透传。
7. **`__set_MSP` 之后能调 C 函数吗?** 不能随便调。当前函数的栈就建在 MSP 上,切换完之后本函数的局部变量全都不在正确位置了——所以 MSP 切换后只能函数指针跳转或裸汇编,不能再碰本函数的栈。我的项目把跳转放在函数最后一句,就是这个原因。

### FreeRTOS 类

8. **7 个任务会不会太多?** 判断标准不是数量,是职责清不清晰。每个任务职责单一、周期明确,总 RAM(任务栈加 TCB)约 10KB,64KB SRAM 余量非常充足。"按职责拆任务"换来的是锁粒度小、逻辑清楚,出问题好定位。
9. **两个同优先级任务(5/5、4/4)?** 时间片轮转。speed/motor、fusion/backflow 各放同组,是因为它们工作耗时短,而且互不竞争同一资源,放一起没有副作用。
10. **为什么 UI 优先级 1 而不是 idle?** idle 要留给系统做空闲处理——钩子函数和低功耗入口;UI 是真实业务,只是"最不急"的那个,不能跟系统空闲混在一起。

### PID 类

11. **稳态误差怎么来的?** 比例控制的输出正比于误差,误差为零输出就为零;而风机负载恒定,必须有非零输出去顶它——所以纯 P 必有静差,必须靠积分项把这笔"欠账"补上。
12. **超调怎么抑制?** 三层手段:积分限幅做抗饱和,不让历史累积推着输出冲过头;前馈把工作点顶到位,减少对积分的依赖;必要时上积分分离,误差大时暂停积分。
13. **如果把 PID 换成整数实现?** 全部乘 1000 定点化,比如 `Kp_e = 2000×e/1000`,fusion.c 里已经是这个风格。F103 没有 FPU,浮点都是软件模拟,定点化能省掉这部分开销。

### 综合/软件工程

14. **代码审查发现过什么问题?** 有四条实打实的:接收无超时会永久死等;Flash 编程没查返回值;跳转前没清 NVIC;最严重的是 APP 链接地址和 bootloader 重叠——从 0x08000000 起编,直接把 bootloader 覆盖了。四个问题全部修复,重新编译验证 0 Err/0 Warn。
15. **验证手段?** 四层:Keil 命令行批量编译保证可重复构建;hex 基址和向量逐字校验;Proteus 仿真验证逻辑(用 `PROTEUS_SIM` 宏隔离硬件依赖);最后上机走完整升级流程,包括 NAK 重传这类注入测试,把异常路径也覆盖到。
16. **项目还能怎么演进?** 我列过清单:双区 A/B 加回滚、固件签名、CAN/UDS、接入 WiFi 模组做真 OTA、PID 自整定(继电反馈法)、编码器换高 PPR。每一项我都说得出动机和代价,不是空喊方向。

### 传感器/架构类

17. **DHT11 读取期间(关中断 <25ms)其他任务怎么办?** 都阻塞在临界区外等锁、等 tick,最坏丢一拍 UI——UI 周期 200ms,人眼无感知。这也正是传感器任务周期放 500ms、优先级放低的原因:**慢活不该打断快活**。
18. **MQ135 读数漂移/受温湿度影响怎么办?** 如实承认没做温湿度补偿,这是已知简化。已做的是上电校准、8 次均值、阈值迟滞;精确方案是 Rs-Ro 标定曲线加湿度修正。主动标注简化点,比被面试官戳穿强一百倍。
19. **怎么给现有架构加蜂鸣器报警?** 不新建任务:backflow/fusion 的状态机置事件标志,UI 任务按标志驱动 GPIO 就行。原则是报警属于"最新状态驱动"而不是"事件流",复用现有 200ms 周期足够;真要微秒级节奏的提示音,才上 TIM PWM 硬件输出。
20. **Proteus 仿真和真机差异怎么管理?** 用 `PROTEUS_SIM` 宏做单点隔离:仿真分支走串口打印、DHT11 给固定值、放宽延时;真机改一个宏重编译就行。方法论一句话:**仿真验证逻辑,真机验证时序**,两个阶段的问题域分开。

## 9. C 语言与嵌入式基础高频题(每一题都有项目出处)

> 嵌入式面试一半的坑在 C 语言基础。下面每题都能落到本项目具体代码,答出来就是"基础扎实 + 真写过"的双重信号。答案为口头回答口径。

**Q1:volatile 什么时候必须用?**

三个场景,我的项目里都有对应代码。一是**硬件寄存器轮询**:dht11.c 里 `while((DWT->CYCCNT - start) < ticks)` 这种等待,如果 CYCCNT 不是 volatile,编译器可能只读一次寄存器,循环条件永远不变,直接死循环;二是 ISR 和主循环共享的变量;三是 bootloader 读 APP 向量时用 `*(volatile uint32_t *)`,防止编译器把"本该发生的读"优化掉。共同点是:这个值会**绕过编译器变化**,编译器必须每次老老实实去读内存。

**Q2:static 的两个作用?**

一个在文件级,一个在函数级。文件内私有:bootloader.c 里所有辅助函数——`uart_dma_block_recv`、`flash_write_byte` 这些——全是 static,**不污染全局命名空间**,编译器也更容易内联;函数内静态:变量**跨调用保持状态**,我的 `s_word_buf` 攒字节计数器就是这么做的。

**Q3:你的协议帧大小端?为什么?**

小端。Cortex-M3 内存就是小端存储,我的组帧代码 `s_word_buf |= b << (cnt*8)` 先到的字节放低位,跟 Flash 的小端**天然一致**;上位机 Python 用 `struct.pack('<I')` 也是同序。只有跨大小端平台传输才需要字节序转换,我两端都是小端,就直接省了这一步。

**Q4:函数指针举例?**

跳转 APP 那一行:`((void (*)(void))app_reset_entry)()`——把向量表第 4 字节的复位处理地址**强转成函数指针直接调用**,就完成了跳 APP。顺带一个细节:这个地址 bit0=1 是 Thumb 语义,由跳转硬件处理,不需要手动置位。

**Q5:强符号/弱符号?**

启动文件里的 Default_Handler 就是弱符号,给所有没实现的 IRQHandler 兜底——忘写某个中断处理函数,**链接不报错但运行死循环**,这是个经典坑。HAL 的回调 `HAL_UART_RxCpltCallback` 也是 `__weak`,用户重写即覆盖。理解了弱符号,HAL 的回调机制就全通了。

**Q6:.text/.rodata/.data/.bss 各放什么?**

.text 放代码;.rodata 放 const 数据,比如字符串表;.data 放有初值的全局——**初值存 Flash,运行时在 RAM 里有一份副本**,启动时拷贝过去;.bss 放零初始化的全局,只占 RAM 不占 Flash。这四段正好对应 1.8 里 map 文件的四个数字:Code/RO/RW/ZI,能对着 map 讲出来就是加分项。

**Q7:位操作举例?**

三个例子都来自我的代码。一是**无分支 CRC**:`(0xEDB88320u & (uint32_t)(0u - (crc & 1u)))` 用掩码代替 if,分支预测友好;二是 NVIC->ICER 的写法——写 1 清使能,写 0 无效,读恒 0;三是 GPIO 的 BSRR **原子置位/复位**,不用读-改-写三步,天然没有竞态。

**Q8:结构体对齐?**

成员按自身对齐数排布,整体对齐到最大成员,所以 sizeof 往往不等于成员之和。这对我的协议设计有直接影响:**跨机传输协议必须逐字节组帧**——我的帧协议就是裸字节流,不 memcpy 结构体,彻底规避对齐和填充在不同编译器上的差异。

**Q9:为什么 bootloader 不用 malloc/printf?**

malloc 有碎片和耗时不确定性,而升级是关键路径,不能容忍"偶尔慢一下";printf 一进来就拉起库依赖,体积膨胀好几 KB。嵌入式关键路径的原则就一句话:**确定性优先于便利性**。

**Q10:轮询超时怎么写才健壮?**

核心是**轮询必须有退出条件**。我的项目里两种写法:计数版是 dht11.c 每一位等待里的 `if(++cnt > 500) return 0xFF;`;tick 版是 bootloader 三级超时里的 `(HAL_GetTick()-t0) > timeout`。前者不依赖时基,后者精度高——但无论哪种,没有退出条件的轮询就是死等的隐患,这是裸机代码的底线。

## 10. 开放性问题与项目叙事(回答脚本)

### 10.1 "这个项目最难的地方是什么?"(STAR 版完整脚本)

> **S(情境):** 决定自研 bootloader 后,第一版烧进去 APP 跑不起来,芯片上电像"没烧过"一样。
> **T(任务):** 嫌疑三方:bootloader 跳转代码、APP 初始化、链接配置——先定位是谁的问题。
> **A(行动):** 从 hex 文件逐行解析入手,发现 APP 数据记录地址从 0x08000000 开始——**向量表偏移改了(VECT_TAB_OFFSET=0x4000),但 Keil 链接地址(IROM)没改**,代码物理上编到了 bootloader 头上,烧 APP 时把 bootloader 直接覆盖。改 OCR_RVCT4 到 0x08004000 重编,用 map 文件确认 LR_IROM1 基址,再核对向量表两项(MSP=0x20004E30 落在 SRAM、Reset=0x08004279 带 Thumb 位)后跳转成功。
> **R(结果):** 一次踩坑把"链接地址 ≠ 向量表偏移"彻底吃透,后来把"hex 首地址 + map 基址"双检查写进了升级流程 checklist(演示见 1.8)。
